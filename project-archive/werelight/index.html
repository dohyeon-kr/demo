Werelight

기존 카페 기반 커뮤니티를 독립 웹사이트로 옮기는 외주 프로젝트에서 기획·디자인과 서버 생성·네트워크를 제외한 애플리케이션 개발 전반을 맡았습니다. WordPress를 CMS·게시판 Backend로 재사용하면서 React 기반 사용자 경험을 만들고, SPA의 SEO/OG 제약을 PHP 서버에서 metadata를 먼저 생성하는 방식으로 우회했습니다.

Context

카페를 사이트로 옮기는 일은 UI 복사가 아니었다

사이트의 목적은 체육 종사자가 새로운 진로를 탐색할 수 있는 커뮤니티를 만드는 것이었습니다. 기존 카페가 가진 게시판과 콘텐츠 운영 기능은 유지해야 했지만, 사용자에게는 별도의 브랜드와 웹 경험이 필요했습니다.

새로운 CMS와 게시판 Backend를 처음부터 만드는 대신 WordPress를 데이터와 운영 도구로 사용하고, React가 실제 사용자 화면을 담당하도록 했습니다. 결과적으로 기존 운영자의 콘텐츠 관리 습관은 크게 바꾸지 않으면서 사용자 인터페이스만 독립적인 애플리케이션으로 가져갈 수 있었습니다.

Product constraint

기존 운영 도구를 버리고 새 시스템을 만드는 것보다, 이미 잘하는 부분은 재사용하고 필요한 경험만 새로 만드는 편이 더 빠르다.

CMS as Product Configuration

운영자가 메뉴를 늘리면 제품도 늘어나게

WordPress 메뉴 기능을 단순 Navigation 텍스트 관리로만 쓰지 않았습니다. 메뉴 항목에 category 정보를 연결할 수 있는 custom field를 두고, 운영자가 메뉴를 추가하면 프론트 Navigation과 해당 category의 게시글 목록이 함께 확장되도록 구성했습니다.

채용 게시판, YouTube 등 외부 영상 embed, 게시판별 추천 글, 일반 게시판에서 채용정보로 바로 이동하는 quick menu도 추가했습니다. 채용 게시판 상단에는 운영자가 지정한 추천 콘텐츠를 우선 노출하고 나머지는 최신순으로 배치했습니다.

03 · JOBS

커뮤니티 콘텐츠에서 직업 피벗 목적에 맞는 채용정보로 자연스럽게 이동할 수 있는 전용 Surface를 만들었습니다.

04 · CURATION

운영자 추천

자동 정렬만 두지 않고 운영자가 중요한 게시물을 우선 배치할 수 있는 편집권을 남겼습니다.

현재 접근 가능한 private repository snapshot에서도 React/TypeScript 기반 프론트엔드가 확인되지만, 저장소 snapshot의 패키지 버전만으로 프로젝트 최초 수행 시점을 단정하지 않습니다. 포트폴리오에는 실제 구현 특성만 사용하고 정확한 기간이 불확실한 정보는 빼두었습니다.

Rendering Constraint

React를 유지하면서 URL metadata를 살리기

CRA 기반 SPA는 React bundle이 실행되기 전에는 실제 콘텐츠가 렌더링되지 않습니다. 브라우저 사용자에게는 큰 문제가 아닐 수 있지만 검색엔진과 소셜 공유의 title, description, Open Graph metadata는 URL별 콘텐츠를 먼저 알아야 했습니다.

당시에는 React 컴포넌트를 서버에서 렌더링하는 Framework를 알지 못했습니다. 그래서 PHP 페이지가 먼저 WordPress API에서 현재 URL에 필요한 데이터를 조회하고 HTML의 metadata와 OG tag를 채운 뒤, 그 HTML 안에 React bundle을 삽입했습니다. 본문 UI는 여전히 Client-side rendering이었습니다.

Request사용자가 특정 콘텐츠 URL로 접근
PHP serverWordPress에서 URL에 맞는 데이터를 읽어 title·description·OG metadata를 생성
HTML response공유·검색에 필요한 metadata를 포함한 기본 문서를 먼저 반환
React bundle브라우저에서 실행돼 실제 인터랙티브 본문을 렌더링

이 방법은 초기 본문 렌더링까지 해결한 SSR은 아니었습니다. 실제로 Client가 bundle을 받은 뒤 화면이 나오는 점을 클라이언트가 의아해했고, 당시에는 React를 유지하려면 이 한계를 받아들여야 한다고 설명했습니다.

Learning

한계가 먼저 있었고, 나중에 Next.js가 연결됐다

이후 Next.js와 SSR을 알게 되면서 당시 문제가 다시 해석됐습니다. React 컴포넌트 기반 개발 경험을 유지하면서 서버가 초기 HTML까지 만들 수 있다는 것을 이해했고, 이후 프로젝트에서는 Server-side props와 SSR을 실제로 사용했습니다.

중요한 점은 Framework 이름을 먼저 공부해 적용한 것이 아니라, 실제 프로젝트에서 SPA의 한계를 몸으로 겪어둔 상태였기 때문에 새로운 추상화의 의의를 빠르게 이해할 수 있었다는 것입니다. 지금도 새로운 기술을 배울 때 기능 목록보다 “어떤 기존 마찰을 해결하려 만들어졌는가”를 먼저 보는 학습 방식과 연결됩니다.
