Native App

기존 웹 서비스를 React Native / Expo 기반 네이티브 앱으로 전환했습니다. 약 한 달 안에 포팅과 스토어 출시를 진행한 뒤, 제품 UI 구조·배포 운영·관측성·협업 방식까지 앱을 지속적으로 운영할 수 있는 개발 시스템으로 확장했습니다.

Context

포팅보다 더 큰 문제

출발점은 이미 운영 중이던 웹 서비스를 네이티브 앱으로 옮기는 일이었습니다. 홈, 포인트, 퀘스트, 출석체크, 장소미션, 응모, 마이페이지와 클릭뷰잉·오토뷰잉·포스팅 같은 기존 적립 기능을 모바일 환경으로 이관하고, 카카오 로그인·소셜 회원가입·계정 연동·SNS 계정 관리·인앱 알림과 푸시까지 연결해야 했습니다.

초기 목표만 보면 화면과 API를 옮기는 포팅 프로젝트처럼 보입니다. 하지만 앱이 스토어에 올라가는 순간 문제는 달라집니다. 디자인 개정이 계속 들어오고, 웹과 앱의 API 계약을 함께 맞춰야 하며, 스토어 심사와 OTA를 구분해서 운영하고, 사용자가 겪는 오류를 실제 요청과 Backend trace까지 따라갈 수 있어야 합니다. 그래서 이 작업을 단발성 포팅으로 끝내지 않고, 출시 이후 변경을 반복할 수 있는 시스템을 만드는 계기로 사용했습니다.

Project thesis

웹을 앱으로 복제하는 것이 아니라, 앱을 계속 바꿀 수 있는 개발·리뷰·배포·관측의 루프를 함께 만든다.

Scope

화면 구현에서 운영 체계까지

앱 구현 범위는 화면을 만드는 데서 끝나지 않았습니다. 실제 운영 과정에서 문제가 발생하는 경계를 따라 제품 구조, 인증 안정성, 릴리즈 체계, 관측, Storybook 기반 협업과 AI 개발 워크플로우까지 역할을 확장했습니다.

01 · APP

웹 기능의 네이티브 이관

핵심 화면군과 적립 기능을 React Native / Expo로 옮기고 실제 API에 연결했습니다. 카카오 로그인·소셜 회원가입·계정 연동과 알림 흐름도 앱에서 다시 배선했습니다.

02 · PRODUCT UI

화면에서 공용 구조를 분리

디자인 토큰, 공용 버튼, 서브헤더, 바텀시트, 모달 호스트, Text/TextInput 래퍼를 공용 레이어로 분리해 화면 단위 수정의 파급을 줄였습니다.

03 · RELEASE

스토어와 OTA 운영 체계

EAS 티어, runtimeVersion baseline, 핫픽스 백머지, prerelease SDK gate와 앱 업데이트 진입점을 정리해 배포 경계를 명확히 했습니다.

04 · OBSERVABILITY

사용자 오류에서 백엔드까지

SigNoz Error Reporting과 traceparent 전파를 연결해 프론트 오류에서 해당 API 요청·응답과 Backend trace까지 탐색할 수 있게 했습니다.

Product UI Architecture

빠르게 바꾸기 위한 구조

ViewUp 2.1 개편에서는 Figma 개정본을 기준으로 화면군을 다시 구현하면서 기존 구현과 디자인 사이의 드리프트를 정리했습니다. 이때 화면마다 스타일을 다시 맞추기보다 디자인 토큰과 공용 컴포넌트를 먼저 분리했습니다. Pretendard와 공용 Text/TextInput 래퍼를 배선해 OS별 한글 폰트·줄바꿈 차이도 공용 계층에서 다뤘습니다.

모달은 여러 화면에서 동시에 present/dismiss가 발생하며 닫히는 중 빈 카드가 보이는 경합이 있었습니다. 이를 Promise 기반 호스트에서 직렬화해 각 화면에서 조건문을 덧붙이는 대신 공용 레이어가 상태 전이를 책임하게 했습니다. 데스크톱 리뷰와 실제 앱 폭의 차이는 440px 앱 프레임을 두어 리뷰 surface와 실행 결과의 차이를 줄였습니다.

인증 실패를 로그아웃으로 굳히지 않기

운영 중에는 일시적인 refresh 실패가 영구 로그아웃으로 이어지는 클라이언트 경로도 확인했습니다. 사용자 세션을 단순 성공/실패 두 상태로 처리하지 않고 실패가 어떤 조건에서 실제 인증 종료로 확정돼야 하는지 경계를 다시 정리해 세 개의 경로를 차단했습니다. 이 작업은 UI보다 작아 보이지만, 앱에서는 사용자의 연속성을 지키는 핵심 안정성 문제였습니다.

Collaboration · AX

코드 리뷰보다 결과 리뷰에 가까워지기

AI가 구현을 맡는 비중이 커질수록 사람이 모든 코드 diff를 기본 검증 단위로 삼는 방식은 병목이 됩니다. 그래서 테스트를 구현 이후 확인 절차가 아니라 작업 경계와 완료 조건으로 적극 사용하고, 반복되는 코드 규칙과 작업 Context는 Skill·Test·Agent workflow에 위임했습니다.

Storybook은 단순 컴포넌트 문서가 아니라 화면 단위 User Flow QA 카탈로그로 재구성했습니다. 디자이너가 UI Picker로 수정 대상을 직접 지정하고 같은 Storybook 화면에서 결과를 다시 확인할 수 있게 했습니다. Picker가 복사하는 결과도 코드 조각 대신 Markdown 링크로 바꿔 사람이 읽기 쉽고, 전달받은 사람이 곧바로 해당 화면으로 이동할 수 있게 만들었습니다.

MSW를 붙여 Backend가 실제 API를 바꾸기 전 응답 변화가 UI에 미치는 영향을 확인할 수 있게 했고, Figma Frame Link와 Layout Verification도 같은 review surface에 넣었습니다. 결과적으로 구현 중간부터 디자인·백엔드·프론트가 같은 화면을 기준으로 이야기할 수 있는 구조가 됐습니다.

Figma를 AI 설명의 원문으로 사용

디자인 변경을 사람이 다시 자연어로 해석해 AI에 설명하는 반복 Context Transfer도 줄였습니다. 공식 Figma MCP로 Agent가 디자인 구조를 직접 읽고, 공식 MCP가 제공하지 못하는 Comment는 별도 Comment MCP로 보완했습니다. Figma 링크 자체가 구현 Context의 entry point가 되고, revision과 comment도 같은 source를 다시 읽어 후속 작업을 이어가는 입력이 됐습니다.

Workflow change

디자인 → 개발자 해석 → AI용 재설명 → 구현의 경로를, 디자인 링크 → Agent 탐색 → 구현·검증으로 단축했다.

Release · Observability

출시 이후를 제품 개발의 일부로

EAS 배포 티어는 development(로컬), preview(TestFlight·APK), production으로 정리했습니다. 정식 릴리즈에서 runtimeVersion이 바뀌면 OTA baseline도 함께 갱신하고, 핫픽스 이후에는 main → develop 백머지 PR을 자동 생성하게 했습니다. production 승격 시 prerelease SDK가 들어가지 않도록 gate를 두고, OTA 즉시 적용·수동 업데이트·서버 지시 앱 업데이트 경로를 구현했습니다.

스토어 운영에서는 iOS의 미사용 권한 문구와 광고 식별자 수집 관련 심사 거절도 대응했습니다. Android release 빌드에서는 R8 코드·리소스 축소를 적용하고, iOS bundle id를 prod/dev로 분리해 환경 간 충돌을 줄였습니다.

관측 측면에서는 Next.js와 Expo 양쪽에 SigNoz Error Reporting SDK를 구축했습니다. 기존에는 프론트에서 발생한 사용자 오류와 Backend trace 사이의 인과관계가 끊겨 있었는데, 요청에 traceparent를 전파하고 리포트 body의 주요 값을 attribute로 승격해 사용자 오류 → API 응답 → Backend trace를 하나의 탐색 흐름으로 연결했습니다.
