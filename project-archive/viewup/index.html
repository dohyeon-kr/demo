Native App

기존 웹 서비스를 React Native / Expo 기반 네이티브 앱으로 전환했습니다. 약 한 달 안에 포팅과 스토어 출시를 진행한 뒤, 제품 UI 구조·배포 운영·관측성·협업 방식까지 앱을 지속적으로 운영할 수 있는 개발 시스템으로 확장했습니다.

Context

포팅보다 더 큰 문제

출발점은 이미 운영 중이던 웹 서비스를 네이티브 앱으로 옮기는 일이었습니다. 홈, 포인트, 퀘스트, 출석체크, 장소미션, 응모, 마이페이지와 기존 적립 기능을 모바일 환경으로 이관하고 카카오 로그인·소셜 회원가입·계정 연동·알림까지 연결해야 했습니다.

하지만 앱이 출시되면 구현 자체보다 화면을 계속 고치고, 스토어와 OTA를 안전하게 운영하고, 실제 사용자 오류를 추적하고, 디자인과 백엔드 변경을 빠르게 검증하는 구조가 더 중요해집니다. 그래서 네이티브 앱 포팅을 단발성 개발 과제가 아니라 이후 운영 방식까지 다시 설계하는 계기로 사용했습니다.

Project thesis

웹을 앱으로 복제하는 것이 아니라, 앱을 계속 바꿀 수 있는 개발·리뷰·배포·관측의 루프를 함께 만든다.

Scope

어디까지 맡았는가

프로젝트 범위는 앱 화면 구현에 머물지 않았습니다. 제품 구조, 인증 안정성, 릴리즈 체계, 관측, 협업 도구까지 실제 운영 과정에서 필요한 경계를 따라 역할을 확장했습니다.

01 · APP

웹 기능의 네이티브 이관

홈·포인트·퀘스트·출석체크·장소미션·응모·마이페이지와 기존 적립 기능을 React Native / Expo로 구현하고 실제 API에 연결했습니다.

02 · PRODUCT UI

화면에서 공용 구조를 분리

디자인 토큰, 공용 버튼, 서브헤더, 바텀시트, 모달 호스트 등 반복되는 UI 구조를 화면 구현에서 분리했습니다.

03 · RELEASE

스토어와 OTA 운영 체계

EAS의 development·preview·production 티어, runtimeVersion baseline, 핫픽스 백머지, SDK gate와 업데이트 진입점을 정리했습니다.

04 · OBSERVABILITY

사용자 오류에서 백엔드까지 추적

SigNoz 에러 리포팅과 traceparent 전파를 연결해 프론트 오류에서 API 응답과 Backend trace까지 따라갈 수 있게 했습니다.

Product UI Architecture

화면을 빠르게 바꾸기 위한 구조

2.1 개편에서는 Figma 개정본을 기준으로 화면군을 다시 구현하면서 디자인 드리프트를 정리했습니다. 디자인 토큰과 공용 컴포넌트를 분리하고, Pretendard 및 공용 Text/TextInput 래퍼를 통해 OS별 한글 폰트·줄바꿈 차이를 줄였습니다.

모달은 여러 화면에서 동시에 present/dismiss가 발생하며 빈 카드가 노출될 수 있었습니다. 이를 Promise 기반 호스트에서 직렬화해 화면 단위 임시 처리가 아니라 공용 레이어에서 경합을 해결했습니다. 데스크톱 리뷰 시 실제 앱 폭과 결과가 달라지는 문제는 440px 앱 프레임을 두어 리뷰 surface와 실제 환경을 최대한 맞췄습니다.

Collaboration · AX

코드 리뷰보다 결과 리뷰에 가까워지기

AI가 구현을 맡는 비중이 커질수록 사람이 모든 코드 diff를 검증하는 방식은 병목이 됩니다. 대신 TDD를 작업 경계와 완료 조건으로 사용하고, 코드 스타일·반복 패턴·작업 맥락은 Skill·Context·Test·Agent workflow에 위임했습니다.

Storybook은 단순 컴포넌트 문서가 아니라 화면 단위 User Flow QA 카탈로그로 재구성했습니다. 디자이너가 UI Picker로 수정 대상을 직접 지정하고 같은 화면에서 결과를 확인할 수 있게 했고, MSW로 실제 백엔드를 수정하기 전에 응답 변경이 UI에 미치는 영향을 확인하도록 만들었습니다.

Figma 역시 사람이 다시 자연어로 설명해 AI에 전달하기보다, 공식 Figma MCP와 Comment MCP를 통해 Agent가 최신 디자인과 코멘트를 직접 읽고 구현하도록 연결했습니다. 디자인 링크 자체가 구현 Context의 진입점이 되도록 한 것입니다.

Workflow change

디자인 → 개발자 해석 → AI용 재설명 → 구현의 경로를, 디자인 링크 → Agent 탐색 → 구현·검증으로 단축했다.

Release · Observability

출시 이후를 제품 개발의 일부로

앱 배포는 EAS 티어를 development(로컬), preview(TestFlight·APK), production으로 정리했습니다. runtimeVersion이 바뀌는 정식 릴리즈에서는 OTA baseline을 함께 갱신하고, 핫픽스 이후 main → develop 백머지 PR을 자동 생성하도록 구성했습니다. production 승격 시 prerelease SDK가 들어가지 않도록 gate를 두고, OTA 즉시 적용·수동 업데이트·서버 지시 업데이트 진입점도 구현했습니다.

관측 측면에서는 Next.js와 Expo 양쪽에 SigNoz Error Reporting을 배선하고, 프론트 요청의 traceparent를 백엔드까지 전파했습니다. 이 구조의 핵심은 특정 관측 도구를 도입한 것이 아니라 사용자가 경험한 오류 → 해당 API 요청·응답 → Backend trace라는 인과관계를 한 흐름으로 볼 수 있게 만든 것입니다.
