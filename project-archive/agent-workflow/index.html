Agent Workflow

AI Agent에게 개발 업무를 더 많이 맡길수록 사람의 코딩 시간이 줄어드는 대신 판단 기준, 작업 경계, 리뷰, 안전성과 측정 방식이 새로운 병목이 됩니다. 반복되는 판단을 문서에만 두지 않고 Agent 정의, Hook, Git workflow, MCP, 관측과 검증 script로 고정한 개인 개발 시스템입니다.

Problem

위임량이 늘면 관리 비용도 늘어난다

AI Agent에게 단순 코드 자동완성보다 큰 작업을 맡기기 시작하면 매번 비슷한 질문이 생깁니다. 이 작업은 구현 Agent가 맡을지 탐색 Agent가 먼저 볼지, 테스트는 어디까지 필요한지, 어떤 명령은 자동 실행해도 되는지, 코드 리뷰를 언제 통과시킬지, 병렬 작업이 같은 Git 상태를 서로 망가뜨리지는 않을지 사람이 계속 결정해야 합니다.

각 세션에서 그 판단을 다시 설명하면 AI 사용량이 늘수록 오히려 Context Transfer와 검수 비용이 커집니다. 그래서 반복되는 판단을 저장소에 규칙으로 남기고, 가능한 것은 Hook과 Script가 실제로 강제하도록 만들었습니다.

AX thesis

AI를 더 많이 쓰는 것이 목표가 아니라, 한 작업을 완료하는 전체 실행 비용과 피드백 비용을 줄이면서 품질을 유지하는 것이 목표다.

Repository Character

문서가 아니라 실행 가능한 작업 시스템

현재 실제 저장소를 다시 보면 구조 자체가 이 의도를 보여줍니다. 역할별 Agent는 `agents`, 강제 규칙은 `hooks`, 지속적으로 적용할 원칙은 `rules`, 외부 도구 연결은 `mcp`, 실행 관측은 `otel`, 설치·검증·리포트 자동화는 `scripts`로 나뉘어 있습니다.

특히 review gate, context guard, subagent audit, test audit 같은 Hook과 그 Hook 자체를 검증하는 verify script가 함께 존재합니다. 즉 “리뷰를 해야 한다”는 문장을 적어두는 데서 끝나지 않고 규칙을 실행하고, 규칙이 제대로 작동하는지도 다시 검증하는 층까지 둔 구조입니다.

01 · AGENTS

역할을 분리

구현, 코드 리뷰, 테스트 작성, lint/type 수정, 컴포넌트 탐색, GitHub, Jira처럼 작업 성격별 Agent를 정의합니다.

02 · HOOKS

규칙을 실행

리뷰 게이트, Context guard, 테스트·서브에이전트 감사처럼 세션의 행동을 자동으로 검사하는 경계를 둡니다.

03 · MCP

원문에 직접 접근

Figma Comment처럼 공식 도구가 제공하지 못하는 Context를 별도 MCP로 연결해 사람이 다시 설명하는 비용을 줄입니다.

04 · OBSERVABILITY

자동화 자체를 관측

OpenTelemetry 설정과 audit log를 통해 Agent 수, 토큰, 테스트·리뷰 결과를 이후 분석 가능한 데이터로 남깁니다.

Delegation

창의성은 열고 리스크는 닫기

모든 작업을 세세한 프롬프트로 통제하면 Agent를 쓰는 의미가 줄어듭니다. 반대로 목표만 주고 모든 판단을 풀어두면 회귀와 작업 충돌을 사람이 사후에 찾느라 비용이 커집니다. 그래서 구현 방법의 자유도는 열어두되, 테스트·Git 상태·리뷰·도구 권한처럼 실패 비용이 큰 경계를 규약으로 닫는 방향을 택했습니다.

Conductor와 Git worktree를 사용해 작업마다 별도 실행 공간을 만들고 여러 Agent를 병렬로 움직입니다. 병렬화의 단위가 단순 채팅 세션이 아니라 독립된 working tree가 되므로, 각 Agent가 파일과 Git 상태를 바꾸어도 다른 작업과 직접 충돌하지 않는 경계를 가집니다.

Review Surface

모든 코드를 읽기보다 결과를 검증

AI가 생성하는 코드량이 커지면 사람이 모든 diff를 기본 검수 단위로 읽는 것은 확장되지 않습니다. 그래서 테스트를 작업 경계로 활용하고, UI 작업은 Storybook과 실제 실행 화면, 프로토타입처럼 사람이 제품 관점에서 판단하기 좋은 Surface를 우선 검토합니다.

코드 리뷰가 사라지는 것은 아닙니다. review Agent와 push gate가 기계적으로 확인할 수 있는 문제를 먼저 걸러내고, 사람은 “실제 제품이 기대한 방식으로 동작하는가”, “설계 경계를 어기지 않았는가”, “사용자 경험이 맞는가”처럼 더 상위의 판단에 집중하도록 역할을 이동시킵니다.

Figma 링크를 설명 대신 Context로

UI 변경에서도 디자인을 사람이 다시 읽고 자연어로 AI에게 번역하는 과정을 줄였습니다. 공식 Figma MCP와 별도 Comment MCP를 사용해 Agent가 디자인 구조와 코멘트를 직접 읽고, 기존 컴포넌트·Storybook과 비교해 수정하도록 연결했습니다. 도구를 새로 만드는 기준도 “멋진 자동화”가 아니라 반복되는 Context Transfer가 실제 병목인가입니다.

Review shift

AI가 구현을 더 많이 맡을수록 사람은 코드 생산자가 아니라 작업 경계와 실제 결과를 검증하는 쪽으로 이동한다.

Measure Forward

효율을 토큰 절감 하나로 보지 않기

자동화가 좋아졌는지를 단순한 토큰 총량으로 판단하지 않습니다. Cache Read가 큰 모델에서는 Raw Token 자체가 실제 비용이나 비효율과 같은 의미가 아니고, AI 사용량을 줄였더라도 사람이 다시 고치는 시간이 늘면 전체 생산성은 나빠질 수 있습니다.

그래서 completed task당 비용과 토큰, 요청 수, 서브에이전트 수, 경과 시간, 사람 개입량을 보고, 동시에 review round, CI 실패, regression·hotfix·rollback 같은 품질 guardrail을 함께 측정하려고 합니다.

Efficiency

tokens/task보다 effective cost와 elapsed time per completed task를 함께 봄

Human Cost

AI 비용이 줄어도 사람의 개입과 재작업이 늘면 개선으로 판단하지 않음

Quality

CI 실패·회귀·핫픽스·롤백을 생산성 지표와 같은 수준의 guardrail로 둠

저장소에 usage report, audit Hook, OpenTelemetry collector와 검증 script가 함께 있는 것도 이 때문입니다. 자동화가 만든 판단 흔적을 남겨야 나중에 실제로 무엇이 좋아졌는지 비교할 수 있습니다.

이 워크플로우는 개인 개발 환경에 적용한 시스템이며 조직의 공식 표준으로 주장하지 않습니다. 현재 목적은 먼저 개인 단위에서 실행 비용과 품질 변화를 측정 가능한 형태로 만드는 것입니다.

What this project shows

AI 위임의 핵심은 프롬프트보다 조직 구조와 비슷한 경계를 만드는 일.

역할을 분리하고, 작업 공간을 격리하고, 테스트와 리뷰 기준을 두고, 결과와 비용을 기록합니다. AI를 하나의 강한 도구로 쓰는 것을 넘어 반복 가능한 개발 시스템 안에 배치하려는 프로젝트입니다.
