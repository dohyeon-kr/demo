Problem

아이디어보다 배포 준비가 먼저 시작되는 문제

작은 실험을 하나 만들 때도 실제 URL로 보여주려면 repository, web server, reverse proxy, SSL, 데이터 저장과 배포 방법을 준비해야 합니다. 아이디어 자체는 몇 시간 안에 만들 수 있는데 공개 환경을 세팅하는 시간이 비슷하게 들면, 결국 실험을 말로만 설명하거나 로컬 프로토타입에서 멈추게 됩니다.

제가 원하는 피드백 방식은 반대였습니다. 기획 설명을 오래 하는 대신 먼저 실제로 작동하는 형태를 공개하고, 사용자가 만져본 결과를 기준으로 이야기하고 싶었습니다. 그래서 한 번 준비해두고 다음 실험부터는 코드를 올리는 일 자체보다 아이디어의 검증에 시간을 쓰게 하는 공용 배포 Surface를 만들었습니다.

Product thesis

프로토타입의 비용을 구현 비용만이 아니라 “남에게 보여줄 수 있는 상태까지 만드는 비용”으로 보고 그 뒤쪽을 플랫폼화한다.

Platform Model

정적 호스팅을 넘어서 작은 제품이 필요한 최소 런타임

처음 목적은 웹 결과물을 빠르게 공개하는 것이었지만 실제 실험을 만들수록 상태 저장, 파일 업로드, 외부 API 호출과 간단한 서버 로직이 필요해졌습니다. 그래서 Publish 기능 위에 프로젝트별 SQLite Data API와 파일, API Key, 제한된 Server Function을 추가했습니다.

01 · PUBLISH

Draft → Preview → Publish

공개 전 Preview와 실제 Publish를 분리하고, 문제가 생기면 이전 Revision으로 Rollback할 수 있게 했습니다.

02 · DATA

프로젝트별 SQLite

각 실험이 별도 DB와 Schema·Record 관리 기능을 가질 수 있어 작은 Backend를 매번 새로 만들지 않게 했습니다.

03 · RUNTIME

Function & Relay

제한된 Server Function과 allowlist 기반 Outbound HTTP Relay로 간단한 서버 처리와 외부 API 연결을 지원합니다.

04 · OPERATIONS

Logs · Backup · Pause

외부 요청과 함수 로그, Backup, 프로젝트 일시정지, 비밀번호 보호를 넣어 실험도 운영 가능한 단위로 다룹니다.

중앙 플랫폼과 프로젝트 데이터 분리

플랫폼 자체의 프로젝트 metadata는 중앙 SQLite에 두고, 각 프로젝트의 실제 데이터는 별도 SQLite DB로 분리했습니다. 거대한 멀티테넌트 데이터 플랫폼을 만드는 대신 단일 노드에서 프로젝트 단위로 이해하고 백업하기 쉬운 경계를 우선했습니다.

Agent Interface

사람용 UI와 Agent용 API를 함께

프로토타입을 AI Agent와 함께 만드는 빈도가 늘면서 배포도 사람이 브라우저에서만 수행하는 작업일 필요가 없었습니다. OAuth MCP를 별도 인터페이스로 두어 Codex나 Claude가 프로젝트를 만들고 결과물을 갱신하는 작업을 직접 수행할 수 있게 했습니다.

이 방향은 “AI가 코드를 만들 수 있으니 배포도 자동화하자”보다 조금 더 넓습니다. 사람이 Admin UI에서 보는 프로젝트 모델과 Agent가 API로 조작하는 프로젝트 모델을 같게 만들어 사람과 Agent가 같은 도구 위에서 다른 인터페이스로 협업하게 하는 실험입니다.

Interface principle

AI Agent를 위한 별도 장난감 환경을 만들기보다, 사람이 실제로 쓰는 시스템에 안전한 조작 인터페이스를 추가한다.

Security Boundary

작은 플랫폼이라도 입력 경계는 작지 않다

파일, DB, 외부 HTTP와 실행 가능한 함수가 한 플랫폼에 모이면 작은 개인 도구라도 위험한 입력이 많아집니다. Secret은 최초 한 번만 보여주고 저장 시에는 hash를 사용하며, filesystem에서는 path traversal과 symlink를 거부합니다. DB 접근은 prepared query와 manifest allowlist를 기반으로 제한했습니다.

외부 HTTP Relay는 허용 목적지를 명시하고 SSRF를 막으며 redirect 이후 목적지도 다시 검증합니다. Server Function도 범용 서버 런타임을 그대로 노출하지 않고 허용된 범위 안에서 실행합니다.

동시에 이 시스템의 한계도 명시합니다. 현재는 single-node와 신뢰 가능한 개인 사용을 전제로 합니다. 서로 신뢰하지 않는 사용자가 임의 코드를 업로드하는 진짜 multi-tenant PaaS라면 process/container isolation과 resource quota 등 훨씬 강한 격리가 필요합니다.

Boundary

현재 가정 아래에서 필요한 안전 경계를 닫되, 그 가정을 넘어선 규모까지 안전하다고 주장하지 않는다.

Meaning

빠른 프로토타이핑을 개인의 반복 가능한 능력으로

PoC Publisher는 하나의 고객 문제를 푸는 제품이라기보다 제가 새로운 제품을 만드는 방식 자체를 개선하는 내부 플랫폼입니다. 아이디어마다 반복되던 공개·데이터·파일·배포 준비를 공통 기반으로 빼면서 다음 실험의 시작점을 높였습니다.

이런 종류의 도구를 만드는 이유는 개발 자체를 자동화하는 데 있지 않습니다. 실체를 빨리 만들고, 그 실체에 대한 사람의 판단을 더 일찍 받는 것이 최종 목적입니다. Storybook, Figma 연결, Agent Workflow와도 같은 방향에 있습니다.

Feedback

아이디어를 설명하는 단계에서 실제 URL을 보여주는 단계로 더 빨리 이동

Reuse

매 실험마다 반복되는 배포·DB·파일·함수 기반을 공용화

Interface

사람과 AI Agent가 같은 프로젝트 모델을 서로 다른 Surface에서 조작

What this project shows

프로토타입을 많이 만드는 사람에게 배포도 제품 개발의 일부다.

PoC Publisher는 개별 아이디어 하나가 아니라 아이디어를 실제로 공개하고 검증하는 전체 루프를 더 빠르게 만들기 위한 개인 플랫폼입니다.
