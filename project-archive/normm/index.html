2021 · Solo Product · UGC

normm

사용자가 직접 이상형 월드컵을 만들고 다른 사람이 플레이하는 UGC 서비스를 기획, 브랜딩, UI/UX, 그래픽 애셋, React 프론트엔드, WordPress API, 카카오 로그인과 클라우드 배포까지 혼자 완성한 졸업작품입니다.

Origin

재미있는 서비스를 직접 만들어보고 싶었다

출발점은 친구들과 이야기하던 이상형 월드컵 서비스 사업 아이디어였습니다. 검색 유입을 확보해 콘텐츠형 캐시카우로 만들 수 있지 않을까 생각했고, 기존 서비스 PIKU를 보면서 제작 경험과 공유 경험을 더 확장할 여지를 찾았습니다.

졸업작품에서는 이 아이디어를 단순 게임 페이지보다 UGC 서비스로 확장했습니다. 사용자가 월드컵을 직접 만들고, 다른 사용자가 플레이하며, 장기적으로는 만든 사람을 팔로우하거나 친구 관계를 중심으로 콘텐츠를 탐색하는 SNS에 가까운 방향까지 생각했습니다.

하지만 졸업전시 일정 안에 그 비전을 모두 구현하는 것은 불가능했습니다. 그래서 제품이 성립하는 최소 핵심을 “월드컵을 만든다 → 플레이한다 → 결과와 통계를 본다”로 잡았습니다. 친구 관계나 Google 이미지 검색 같은 아이디어는 뒤로 미루고 이 흐름의 완성을 우선했습니다.

Product priority

비전의 크기보다 사용자가 처음부터 끝까지 한 번 완주할 수 있는 핵심 경험을 먼저 완성한다.

Ownership

제품 전체가 한 사람의 책임 범위

브랜드 이름과 로고, 모바일 중심 화면 디자인, 그래픽 애셋, 서비스 로직과 API까지 한 프로젝트 안에서 직접 다뤘습니다. React 프론트엔드와 WordPress Custom REST API를 연결하고, 카카오 로그인과 JWT 기반 사용자 흐름, 이미지 업로드, 토너먼트 상태와 통계를 구현했습니다.

지금의 기준으로 보면 기술 선택과 코드 구조에 부족한 점이 많지만, 이 프로젝트는 특정 레이어의 완성도보다 아이디어가 실제 사용 가능한 제품이 되기 위해 어떤 레이어들이 연결되어야 하는지를 처음부터 끝까지 경험한 작업이었습니다.

01 · PRODUCT

기획과 우선순위

UGC SNS라는 장기 비전에서 전시 기간 안에 반드시 완성할 핵심 사용자 흐름을 잘라냈습니다.

02 · DESIGN

Brand & UI/UX

서비스명, 로고, OG 이미지, 모바일 중심 UI와 각 화면의 그래픽 요소까지 직접 설계했습니다.

03 · APPLICATION

React Frontend

생성·플레이·통계·검색·로그인·댓글과 반응 기능을 실제 앱 흐름으로 구현했습니다.

04 · BACKEND

WordPress as API

Custom REST endpoint와 사용자/JWT, 후보·토너먼트·댓글·파일 데이터를 WordPress/PHP 위에 구성했습니다.

Repository Character

코드 구조에도 핵심 플로우가 그대로 남아 있다

현재 공개된 GitHub 저장소를 다시 살펴보면 `Making`, `Tournament`, `Statistic`이 최상위 페이지로 독립해 있습니다. `apis`, `hook`, `redux`, `components`도 별도 계층으로 존재합니다. 이 구조는 졸전에서 보여주기 위한 몇 장의 화면을 만든 것이 아니라, 생성→플레이→결과라는 제품 플로우가 애플리케이션의 실제 구조를 결정했다는 점을 보여줍니다.

Making제목·설명·공개 상태를 정하고 최소 4개의 후보를 등록해 월드컵 자체를 생성
Bulk upload한 장씩 추가하는 불편을 줄이기 위해 multiple file과 drag & drop으로 여러 후보를 순차 업로드
Tournament라운드를 선택하고 두 후보 중 하나를 반복 선택하면서 서버의 토너먼트 상태를 갱신
Statistic후보 순위·매치 승률·토너먼트 승률·플레이 수·좋아요·댓글을 결과 경험으로 연결

특히 “만들기”가 단순 관리자 기능이 아니라 일반 사용자의 핵심 기능이라는 점이 중요했습니다. 제작자가 후보를 여러 개 빠르게 올리고 이름을 수정하고 이미지를 교체할 수 있어야 콘텐츠가 생기고, 그 콘텐츠가 플레이와 통계로 이어져야 서비스가 순환합니다.

제작 UX에서 먼저 발견한 업로드 문제

기존 서비스에서 이미지를 한 장씩 추가해야 하는 과정이 번거롭다고 느꼈습니다. 이를 해결하기 위해 다중 이미지 선택과 Drag & Drop을 지원했습니다. 여러 파일을 업로드하는 동안 비동기 상태가 서로 꼬이지 않게 순서를 제어하는 과정은 당시 상당히 어려웠고, 검색과 실험으로 해결했습니다.

이 경험은 이후 KHVD 같은 대량 이미지 업로드에서도 사용자는 업로드가 멈췄는지 진행 중인지 알 수 있어야 한다는 관점으로 이어졌습니다. 특정 라이브러리를 기억하는 것보다, 사용자의 기다림을 제품 상태로 표현해야 한다는 교훈이 남았습니다.

Engineering

스스로 연결하며 배운 웹의 레이어

프론트엔드에서는 React 17, Redux, styled-components와 React Router를 사용했습니다. Backend는 WordPress와 PHP였고, 프론트가 `data.normm.me`의 REST API와 통신하는 구조였습니다. 이미지 업로드는 multipart/form-data, 인증은 Kakao Login과 JWT Bearer token을 사용했습니다.

당시에는 이 기술들을 누군가에게 체계적으로 배운 상태가 아니었습니다. 필요한 기능을 만들기 위해 인증은 어떻게 연결되는지, 브라우저가 파일을 HTTP로 어떻게 보내는지, 서버가 토너먼트 상태를 어떻게 기억해야 하는지를 하나씩 찾아가며 조립했습니다.

그래서 완성 이후에는 반대로 한계도 명확하게 보였습니다. 구현이 동작하기는 하지만 많은 판단이 즉흥적이고, 테스트나 반복 가능한 설계 규칙이 부족했습니다. “어떻게든 만든다” 다음 단계에는 “다시 만들어도 비슷한 품질을 낼 수 있는 과정”이 필요하다는 문제의식이 생겼고, 이후 소프트웨어 공학과 개발 워크플로우에 관심을 갖는 계기가 됐습니다.

공개 저장소에는 장기 비전의 흔적이 UI 문구로 일부 남아 있지만, 친구 관계나 Google 이미지 검색이 완전히 동작했다고 보지는 않습니다. 포트폴리오에는 실제 구현이 확인되는 생성·플레이·통계·검색·반응 기능만 성과로 다룹니다.

Retrospective

기능 완성과 제품 성과는 다르다

서비스는 실제로 공개됐지만, 졸업전시 이후 적극적인 홍보와 후속 운영을 거의 하지 않았습니다. 기능은 완성됐지만 사용자가 충분히 유입되지 않았고, 결과적으로 제품으로서의 성장까지 이어지지는 못했습니다.

이 경험은 “잘 만들었다”를 기능의 존재만으로 판단하지 않게 만든 초기 실패이기도 합니다. 지금 다시 만든다면 기능 개발과 동시에 유입 경로, 콘텐츠 공급, 재방문 이유와 운영 주체를 함께 설계했을 것입니다.

What remained

처음부터 끝까지 혼자 만들 수 있다는 자신감과, 완성도만으로는 제품이 성공하지 않는다는 경계가 동시에 남았다.

What this project shows

디자인에서 개발로 전환한 것이 아니라, 제품 전체를 직접 만들기 시작한 시점.

normm은 특정 기술 숙련도를 보여주는 프로젝트라기보다 아이디어·브랜드·사용자 경험·데이터·배포를 하나의 시스템으로 연결해본 첫 end-to-end 제품입니다.
