Context

결과물의 형태보다 필요한 시스템

기획과 디자인을 제외한 애플리케이션 구현과 운영을 담당했습니다. 이 프로젝트를 계기로 AWS 사용법을 익히고 서버 인스턴스까지 직접 관리하기 시작했습니다. 당시에는 아직 스스로를 특정 개발 직군의 역할로 나누기보다, 전시를 실제로 운영하는 데 필요한 것이 있으면 그 형태에 맞춰 만들었습니다.

웹사이트가 필요하면 React와 WordPress를 사용했고, 다량의 데이터를 다뤄야 하면 Python으로 전처리했으며, 현장 판매 기록이 문제라면 Excel을 만들었습니다. Web, API, Script, Spreadsheet가 각각 다른 직무의 산출물이 아니라 같은 운영 문제를 해결하는 도구라는 관점이 이때 이미 나타납니다.

Working principle

무엇으로 만들었는가보다 실제 현장에서 무엇이 덜 틀리고, 덜 반복되고, 더 쉽게 운영되는지가 중요했다.

Product Surface

졸업전시 소개 페이지보다 큰 제품

현재 남아 있는 GitHub 저장소를 다시 보면 프로젝트 성격이 더 분명합니다. 최상위 화면이 Intro와 Main에만 머물지 않고 Participant, ParticipantList, Project, ProjectCategory, Guestbook, MyDashboard, PopupStore처럼 독립된 사용자 흐름으로 나뉘어 있습니다. 컴포넌트 층에도 Dashboard UI, Editor, Guestbook Editor·Viewer 같은 운영·작성 기능이 별도로 존재합니다.

즉 이 프로젝트는 정적인 온라인 전시관보다는 참가자가 자신의 작품 정보를 관리하고, 관람자가 작품과 참가자를 탐색하고, 전시와 관련된 부가 기능을 사용하는 작은 운영형 플랫폼에 가까웠습니다. Career 저장소에 남은 기록과 실제 GitHub 구조가 이 성격을 서로 보강합니다.

01 · DISCOVERY

참가자와 작품 탐색

참가자 목록, 작품 상세, 작품 카테고리를 독립 흐름으로 두어 전시물을 사람과 작품 두 축에서 탐색할 수 있게 했습니다.

02 · PARTICIPANT

개인 관리 Surface

로그인과 개인 Dashboard가 별도로 존재해 참가자가 자신의 전시 정보를 관리하는 운영 흐름을 지원했습니다.

03 · INTERACTION

방명록

방명록은 단순 텍스트 리스트가 아니라 Editor와 Viewer가 분리된 별도 상호작용 영역으로 구현됐습니다.

04 · COMMERCE

Popup Store

웹서비스 안에 팝업스토어 진입점이 따로 존재했고, 실제 오프라인 굿즈 판매 운영과도 연결되는 맥락을 가졌습니다.

콘텐츠 편집도 직접 만든 Surface

저장소에는 Editor 계층과 editor plugin 디렉터리가 별도로 존재합니다. 이는 외부 CMS 화면만 사용하는 방식이 아니라, 참가자나 운영자가 실제 전시 데이터와 콘텐츠를 다루는 경험을 애플리케이션 내부에 가져오려 했던 흔적입니다. 지금의 눈으로 보면 거칠고 오래된 구현도 있지만, 사용자용 화면과 운영 화면을 하나의 제품 경계로 보는 관점은 이후 프로젝트에서도 반복됩니다.

Operations

사이트가 공개되는 순간부터 운영 문제

애플리케이션 배포뿐 아니라 AWS 서버 인스턴스를 직접 관리했습니다. CloudFront와 S3 같은 서비스를 접하고, 라이브 스트리밍을 위해 RTMP/HLS 구성도 다뤘습니다. 전시라는 짧은 기간 안에 실제 사용자가 몰리고 콘텐츠가 계속 바뀌기 때문에, 단순 개발 완료보다 행사 기간 동안 계속 살아 있는 시스템으로 다루어야 했습니다.

참가자별 이미지와 작품 자료는 형식과 크기가 제각각이었고, 배포 가능한 데이터로 정리하는 작업이 필요했습니다. 이미지의 사용 기준을 맞추고 카탈로그 데이터를 일괄 처리하는 도구를 만들면서, 사람이 파일 하나씩 손으로 정리하는 대신 입력 데이터를 시스템이 받아들일 수 있는 형태로 정규화하는 경험을 쌓았습니다.

Source material참가자·작품·이미지·카탈로그처럼 제각각 들어오는 전시 데이터

Application웹서비스가 같은 데이터 구조를 기준으로 참가자·작품·운영 화면을 제공

On-site Automation

현장 판매의 입력을 한 번으로 줄이기

굿즈 판매 현장에서는 판매 기록, 재고, 전체 매출, 판매 주체별 정산을 각각 적고 있었습니다. 같은 판매 사실을 여러 장부에 반복 입력해야 했고, 바쁜 현장에서는 한 군데만 빠뜨려도 나중에 맞추기 어려워졌습니다.

별도 요청을 받기 전에 판매 입력을 하나의 주 입력원으로 삼는 Excel 장부를 만들어 제안했습니다. 판매를 한 번 기록하면 여러 Sheet에서 재고, 전체 매출, 판매 주체별 정산금과 마감 결과가 자동으로 파생되도록 구성했습니다. VBA나 별도 프로그램 없이 Excel 함수만 사용해 현장 PC에서 즉시 사용할 수 있게 했습니다.

동시성을 만들지 않는 것도 설계

입력 Client를 여러 개로 늘리는 것도 가능했지만 실제 현장에는 캐셔 PC 한 대와 기록 담당자 한 명이 있었습니다. 그래서 복잡한 다중 사용자 시스템을 만들지 않고 single-writer 방식으로 사용했습니다. 기술적으로 더 복잡한 구조를 만드는 것보다 실제 운영 모델에 맞춰 필요한 만큼만 시스템화한 선택입니다.

Input

한 번의 판매 기록을 재고·매출·정산의 공통 원천으로 사용

Operation

전시 종료까지 실제 현장에서 계속 사용하며 마감과 재고 확인을 지원

Pattern

사람이 기억하거나 중복 입력하는 지점을 줄이는 방식이 이후 자동화에도 반복

Long-term pattern

한 번의 입력에서 여러 결과를 파생시키고, 사람이 같은 사실을 다시 적는 지점을 없앤다.

Learning

개발자가 되기 전부터 개발자처럼 일한 프로젝트

이때는 소프트웨어 공학의 언어나 인프라 원리를 체계적으로 알고 있지 않았습니다. 하지만 필요한 운영 흐름을 관찰하고, 반복 입력과 누락 지점을 찾고, 도구를 스스로 배워 실제 사용 가능한 형태로 바꾸는 방식은 이후에도 거의 변하지 않았습니다.

현재 돌아보면 이 프로젝트의 가장 큰 의미는 React나 AWS를 처음 썼다는 데 있지 않습니다. 화면 밖의 현장까지 제품의 일부로 보고, 문제에 따라 웹·서버·스크립트·Excel의 경계를 넘나들었던 초기 사례라는 점입니다.

What this project shows

문제에 맞춰 도구의 경계를 넘는 방식은 아주 일찍부터 있었다.

웹사이트, 참가자 관리, 작품 데이터, 서버 운영, 스트리밍, 현장 판매 장부를 따로 떨어진 업무로 보지 않고 하나의 전시 운영 문제 안에서 다뤘습니다.
