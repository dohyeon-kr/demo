만나로 ·
대치4동 산등성길

서울신용보증재단 골목상권 활성화 사업에서 제휴 상점을 소개하고 5천 원 할인 쿠폰으로 오프라인 방문과 결제를 유도한 서비스입니다. 기획·정책·UI 디자인·상점 콘텐츠를 제외하고 기술 설계, Next.js 프론트, NestJS·Prisma/MySQL API, 관리자·상점 기능, 알림, Jenkins·Docker 배포와 운영 도구를 1인 개발했습니다.

Platform

쿠폰 화면보다 운영 플랫폼

사용자에게 보이는 핵심은 지도에서 상점을 찾고 5천 원 쿠폰을 받아 현장에서 사용하는 일이었습니다. 하지만 실제로 서비스를 운영하려면 상점 계정, 발급 제한, 예산, 쿠폰 사용·취소, 관리자 통계와 리포트까지 함께 움직여야 했습니다.

Career 저장소의 코드 조사에서는 상점 검색·지도·상황별 맛집 추천, 관리자 예산과 주차별 발급·사용·만료 통계, 상점 계정과 RBAC, PWA, S3 이미지, 쿠폰 취소·사용 관리와 리포트가 확인됩니다. 즉 사용자용 프로모션 페이지가 아니라 사용자·상점·운영팀이 각기 다른 권한으로 같은 쿠폰 상태를 다루는 작은 상권 운영 플랫폼이었습니다.

동작구 1기의 실패를 다시 공부하는 계기로

이전 동작구 쿠폰에서 중복 발급 문제가 있었고, 후속 시스템을 만들면서 NestJS의 트랜잭션 문서를 다시 학습했습니다. `nestjs-cls`와 Prisma 요청 단위 트랜잭션을 이용해 사용자 생성, 발급 제한 확인과 실제 쿠폰 발급을 같은 문맥에 묶었습니다.

다만 만나로 시점에는 Serializable이나 명시적 락까지 적용하지 않았기 때문에 레이스를 완전히 제거했다고 말하지 않습니다. 실제 동시성 CS는 기억나지 않지만, 사고가 없었다는 것과 구조적으로 안전하다는 것은 다른 문제입니다. 이 부족한 지점은 2025 동작42에서 더 강한 격리와 상태 전이 설계로 이어졌습니다.

Evolution

한 번의 프로젝트에서 완성된 정답을 얻은 것이 아니라, 운영과 실패를 다음 프로젝트의 설계 깊이로 계속 옮겨갔다.

Iteration

만나로를 만들고, 대치에서 정책을 고쳤다

만나로에서는 상점마다 같은 수량을 고정 배정했습니다. 운영해보니 상점별 소진 속도 차이가 컸고, 어떤 곳은 빨리 소진되는 반면 다른 곳에는 예산이 남았습니다. 후속 대치4동 시스템에서는 관리자가 상점별 최대 발급량을 숫자로 바꾸고, 서버의 발급 가드가 최신 값을 즉시 반영하도록 개선했습니다.

흥미로운 부분은 이 최대 발급량을 현재 값 하나로 덮어쓰지 않았다는 점입니다. 코드 조사에서는 `maximumCouponCount` 변경값을 append-only로 쌓고 생성일 기준 가장 최근 값을 현재 정책으로 사용하는 구조가 확인됩니다. 완전한 감사 로그는 아니지만 운영 정책도 시간이 지나며 변하는 데이터이며, 이전 상태를 지우지 않는 편이 추적에 유리하다는 방향이 나타납니다.

Merchant Operations

한 건의 CS를 범용 설정으로

GS25 한 상점에서는 부부가 함께 운영하고 있었지만 쿠폰 사업 참여 의사가 서로 달랐습니다. 아내가 근무하는 요일과 시간에만 쿠폰 사용을 받고 싶다는 요청이 들어왔습니다. 특정 상점만을 위한 조건문을 추가하는 대신 상점마다 사용 요일·시간·주의사항·확인 비밀번호를 설정할 수 있도록 일반화했습니다.

요일과 시간은 서버가 강제로 사용을 막는 hard rule로 만들기보다 발급 전 모달과 상점 화면에 조건을 노출하는 방식이었습니다. 정책의 성격에 따라 시스템이 강제해야 하는 규칙과 현장에서 안내해야 하는 규칙을 구분한 것입니다.

Operational pattern

개별 민원을 예외 코드로 쌓지 않고, 다른 상점에도 쓸 수 있는 운영 설정으로 번역한다.

알림은 구현됐지만 정착하지 않았다

이전 사업에서 상점주가 “쿠폰이 사용된 사실을 바로 알기 어렵다”고 했기 때문에 웹 푸시로 상점과 관리자에게 즉시 알림을 보내는 기능도 만들었습니다. 하지만 구독 절차가 어렵고 운영팀의 현장 안내도 충분하지 않아 상점 도구로는 정착하지 못했습니다. 결과적으로 개발자가 운영 상황을 확인하는 수단으로 더 많이 쓰였습니다.

기능을 만들었다고 채택이 보장되지는 않는다는 사례입니다. 현장 사용성이 중요한 기능은 구현뿐 아니라 온보딩과 운영 프로세스까지 함께 설계해야 합니다.

Result

예산을 소진하는 것과 시스템을 배우는 것

두 사업 모두 배정된 쿠폰 예산은 전액 소진된 것으로 확인됩니다. 보관 데이터 기준 상점은 각 사업 약 20곳 내외지만 삭제·추가·누락 가능성이 있어 정확한 참여 상점 수로 외부 표기하지 않습니다.

더 중요한 결과는 후속 설계에 남았습니다. DB 트랜잭션과 외부 문자·웹 푸시를 같은 실패 경계에 넣지 않도록 알림을 별도 문맥에서 처리했고, 고정 배정의 운영 문제는 수정 가능한 정책으로, 개별 상점 CS는 재사용 가능한 설정으로 바뀌었습니다.
