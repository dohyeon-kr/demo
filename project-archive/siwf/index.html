작가축제

2022 서울국제작가축제의 사용자 웹사이트와 전용 관리자 화면을 개발했습니다. 기획·디자인이 완료된 상태에서 애플리케이션 개발 전반을 맡았고, 이후 획기획 입사 후에는 같은 프로젝트의 클라우드 전환 과정에서 사설망 환경에 맞춰 애플리케이션을 다시 정상화했습니다.

Context

콘텐츠 사이트와 운영 도구를 하나의 제품으로

사용자에게는 작가, 프로그램과 행사 콘텐츠를 보여주는 축제 웹사이트였지만, 운영자 관점에서는 행사 기간 동안 계속 콘텐츠를 수정하고 노출 순서를 바꾸어야 하는 시스템이었습니다. WordPress를 데이터 원천이자 REST API 계층으로 사용하고, 사용자 화면과 관리자 화면은 하나의 Next.js 애플리케이션 안에서 구성했습니다.

Career 저장소에 남아 있는 백업 구조에서도 Next.js 앱의 페이지·배너·메뉴 관련 컴포넌트와 API hook, WordPress의 headless theme가 함께 확인됩니다. 즉 WordPress 테마가 사용자 화면을 직접 렌더링하는 전통적인 CMS가 아니라, WordPress는 콘텐츠·API를 맡고 Next.js가 실제 사용자 경험을 책임하는 headless 구조였습니다.

Architecture shift

이 프로젝트를 거치며 PHP 페이지를 만드는 관점에서 벗어나 client / API / DB가 서로 독립적인 역할로 분리될 수 있다는 구조를 실무에서 이해하기 시작했다.

CMS 제약을 큰 개편 없이 우회

일부 콘텐츠는 WordPress 본문 에디터가 아니라 metadata 필드에 저장됐습니다. 하지만 문장 일부에 italic, bold, 줄바꿈 같은 표현이 필요했습니다. 별도의 대형 Rich Text Editor를 도입하기보다 운영자가 입력할 수 있는 작은 토큰 문법을 만들고, 프론트에서 문자열을 파싱해 표현으로 바꿨습니다.

지금 보면 Markdown이나 구조화된 rich text 모델을 고려할 수 있지만, 당시 선택은 기존 WordPress 데이터 구조를 크게 흔들지 않고 필요한 표현만 추가하는 쪽이었습니다. 이 프로젝트에서 반복되는 판단은 “더 좋은 기술을 새로 넣는 것”보다 이미 존재하는 운영 구조를 최소 비용으로 확장하는 것이었습니다.

Admin UX

운영자가 데이터가 아니라 화면을 보며 편집하게 하기

WordPress 기본 관리자 화면을 깊게 커스터마이징하면 기존 CMS 내부 구조와 싸워야 했습니다. 대신 같은 Next.js 프로젝트에 전용 admin route를 만들고, 사용자 페이지의 레이아웃과 맥락을 그대로 가져오되 실제 콘텐츠가 바뀌는 부분을 input과 편집 UI로 교체했습니다.

운영자는 추상적인 필드 이름만 보고 수정하는 대신 실제 사용자가 보는 화면과 유사한 맥락 안에서 배너와 메뉴를 관리할 수 있었습니다. 배너 노출 순서를 Drag & Drop으로 변경하고, 메뉴 항목 추가·삭제·순서·링크·노출 여부를 조정할 수 있게 했습니다.

반복되는 WordPress API를 작은 프레임워크로

Custom REST endpoint를 반복해서 만들다 보니 요청·응답 공통 처리와 많은 생성 인자를 매번 작성하는 비용이 생겼습니다. 이를 class로 모듈화하고 기본값을 제공해 다른 WordPress 프로젝트에도 파일 단위로 재사용했습니다. 당시에는 private package 배포 체계를 알지 못해 파일 복사 방식이었지만, 이미 반복 작업을 추상화해 다음 프로젝트의 시작 비용을 낮추려는 방향은 나타나고 있었습니다.

Integration

외부 게임도 같은 데이터 흐름에 연결

행사 안에는 외부 게임 개발자가 만든 타자게임도 포함됐습니다. 디자이너가 게임 화면을 기획했고, 저는 게임에 필요한 데이터가 무엇인지 외부 개발자와 맞춘 뒤 WordPress Custom REST API에서 필요한 형태로 제공했습니다.

게임 번들은 ZIP으로 전달받아 서버에서 수동 교체했습니다. 실제 버전 사고까지 이어지지는 않았지만, 반복되는 artifact 전달과 교체가 번거로웠습니다. 지금이라면 같은 생명주기의 코드는 monorepo에서 함께 빌드하거나, 독립 저장소라면 CI가 artifact를 전달하는 구조로 만들겠지만, 이 경험은 이후 코드 경계뿐 아니라 배포 경계도 자동화 대상으로 보게 된 초기 사례였습니다.

Cloud Transition

SSR은 어디에서 요청하는가

클라우드 이전 자체는 전문 대행사가 담당했습니다. 저는 백업을 전달한 뒤 이전된 환경에서 애플리케이션 프로세스를 다시 올리고 정상화하는 역할을 맡았습니다. 이때 처음으로 사설망과 outbound 제약을 실제 장애로 경험했습니다.

기존 Next.js SSR은 WordPress API의 외부망 주소를 호출하도록 구성돼 있었습니다. 이전된 서버는 사설망에 있고 외부 outbound가 막혀 있었기 때문에 서버에서 WordPress API를 호출할 수 없었습니다. 당시에는 내부 IP나 내부 통신 경로를 별도로 설계한다는 개념이 충분하지 않았습니다.

반면 사용자의 브라우저에서는 외부 WordPress API에 접근할 수 있었습니다. 그래서 문제가 되는 부분을 CSR로 전환해 서비스를 정상화했습니다. 완벽한 네트워크 설계로 해결한 사례는 아니지만, 이 사건은 SSR과 CSR을 단순히 SEO나 렌더링 속도 차이로 보던 관점을 바꿨습니다.

Mental model

렌더링 방식의 차이는 결국 “그 요청이 어느 네트워크 위치에서 출발하는가”의 차이이기도 하다.

이 경험은 이후 직접 클라우드를 구성하면서 내부망·외부망을 분리하거나 VPN을 이해하는 기반이 됐습니다. 기술 개념을 문서로 먼저 외운 것이 아니라, 실제 실패를 겪고 나서 네트워크 모델이 뒤늦게 연결된 사례입니다.

Verification

정상 상태를 문서로 공유한 첫 경험

클라우드 전환 대행사는 이전 이후 무엇을 정상으로 판단할지 반복적으로 물었습니다. 당시 자동화 테스트 경험은 거의 없었지만, 사용자 기능별로 정상 동작을 확인하는 수동 E2E 항목을 직접 정의했습니다.

중요했던 것은 테스트 기술 자체보다 애플리케이션의 정상 상태를 개발자의 머릿속 감각에서 꺼내 외부 업체와 공유 가능한 검증 기준으로 바꿨다는 점입니다. 이후 테스트를 구현 확인이 아니라 작업 계약과 회귀 경계로 사용하는 방향의 아주 초기 경험이 됐습니다.

What this project shows

웹 개발에서 시스템 구조로 시야가 넓어진 전환점.

사용자 화면과 관리자, CMS, 외부 게임, 서버와 네트워크가 하나의 서비스 안에서 만났습니다. 완벽한 설계를 처음부터 알고 시작한 것이 아니라, 실제 제약을 해결하면서 클라이언트·API·네트워크 경계에 대한 멘탈 모델을 만든 프로젝트입니다.
