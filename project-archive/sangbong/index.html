기획과 디자인을 제외하고 공개 웹, 상점 스태프 화면, API와 데이터 모델, PASS·OAuth 인증, 영수증 OCR, 쿠폰·정산 백오피스, 배포와 행사 운영 대응까지 애플리케이션 개발 전반을 혼자 담당한 지역 상권 이벤트 서비스입니다.

Context

하나의 축제에 여러 참여 방식

이 서비스는 쿠폰을 한 번 발급하고 끝나는 이벤트가 아니었습니다. 사용자는 사연을 제출해 선정될 수도 있고, 행사 기간의 영수증을 인증해 보상을 받을 수도 있고, 당첨 이후 후기를 남기거나 성향 테스트를 공유할 수도 있었습니다. 상점은 쿠폰을 현장에서 사용 처리하고 정산 자료를 확인해야 했으며 운영자는 당첨·영수증·쿠폰·정산 상태를 추적해야 했습니다.

Career 저장소의 코드 조사에서는 사용자, OAuth 계정, PASS 거래 이력, 상점·상점그룹, 스태프, 사연, 후기, 영수증, 쿠폰, 정산 회차와 정산 상태가 각각 별도 모델로 관리된 것이 확인됩니다. 이것은 화면이 많은 이벤트 사이트라기보다 서로 다른 참여 규칙을 하나의 사용자·상점·보상 모델 안에서 조정하는 행사 운영 시스템에 가까웠습니다.

Product character

“이벤트 페이지”가 아니라 참여 자격, 증빙, 보상, 사용, 정산이라는 상태를 끝까지 이어주는 시스템.

Participation Flows

참여 자격을 서버가 판단하게 하기

사연 이벤트에서는 사용자가 기간, 동행인과 사연을 제출하고 운영자가 선정 시각을 기록했습니다. 선정된 사연에는 쿠폰이 연결되고, 이후 후기 작성 가능 여부는 해당 쿠폰 보유 여부와 기존 후기 존재 여부를 서버에서 다시 확인했습니다.

후기는 10~200자의 텍스트와 이미지가 필요했고 선정 사연마다 한 번만 작성할 수 있었습니다. 늦게 쿠폰을 받은 당첨자를 위한 추가 기간도 별도로 고려됐습니다. 이런 규칙을 화면에서만 숨기거나 보여주는 대신 서버가 “현재 이 사용자가 실제로 참여 가능한가”를 판단하도록 구성했습니다.

01 · STORY

사연 제출과 선정

기간·동행인·사연을 제출하고 운영자가 선정하면 보상 쿠폰과 후속 후기 흐름을 연결했습니다.

02 · REVIEW

후기 자격과 중복 방지

쿠폰 보유와 기존 작성 여부를 서버에서 확인해 선정된 사용자의 1회 후기 흐름을 관리했습니다.

03 · TEST

케미 성향 테스트

선택지 순서를 섞고 점수 유형에 따라 결과를 만들며 공유와 이미지 저장까지 별도 콘텐츠 경험으로 구성했습니다.

04 · COUPON

현장 사용

소유권·사용 가능 기간·중복 사용 여부를 서버가 확인한 뒤 현장에서 쿠폰을 사용 처리했습니다.

Receipt OCR

사진 한 장을 보상 가능한 증빙으로

영수증 이벤트에서는 사용자가 행사 기간의 영수증을 업로드하면 OCR로 상점, 일시와 금액을 추출했습니다. 서버는 행사 기간인지, 참여 상점인지, 금액이 3만 원 이상인지 확인한 뒤 조건을 충족한 참여를 보상 대상으로 다뤘습니다.

영수증 이미지는 같은 파일을 그대로 다시 올릴 수도 있고, 재저장하거나 캡처해 파일 자체가 달라질 수도 있습니다. 그래서 코드 조사에서는 파일 자체의 SHA-256과 함께 날짜·시간·상점·금액으로 만든 내용 기반 지문을 같이 사용한 것이 확인됩니다. 파일 동일성과 영수증 의미의 동일성을 두 층으로 확인해 중복 제출을 줄이려 한 구조입니다.

Upload사용자가 행사 기간 영수증 이미지를 제출
OCR상점·일시·금액을 구조화된 값으로 추출
Validation행사 기간·참여 상점·최소 금액과 중복 여부를 확인
Reward조건을 충족한 선착순 참여자에게 5천 원 쿠폰을 연결

OCR은 입력을 자동으로 읽어주는 편의 기능이지만, 제품 입장에서는 추출된 값을 그대로 믿지 않고 실제 이벤트 규칙과 다시 대조해야 했습니다. 자동화의 출력도 다른 외부 입력과 마찬가지로 검증 대상이라는 특성이 드러나는 부분입니다.

Backoffice

행사 상태가 운영자에게 보이게

상점 스태프는 휴대전화 인증과 비밀번호 재설정을 거쳐 연결된 상점의 쿠폰 매출과 일별 사용액을 확인했습니다. 운영자 측에서는 영수증 OCR 결과, 중복 여부, 쿠폰 발급·사용 상태, 정산 회차와 증빙 이미지, 정산 상태와 메모 이력을 추적할 수 있게 했습니다.

공개 화면에서 “참여 완료”라고 보여주는 것과 실제 운영 상태가 다르면 행사 CS가 급격히 어려워집니다. 그래서 참여 결과와 리뷰 가능 상태를 서버 기준으로 제공하고, 백오피스에는 그 판단의 근거가 되는 데이터를 남기는 방향으로 구성했습니다.

User

사연·영수증·후기·테스트처럼 서로 다른 참여 흐름을 하나의 계정으로 연결

Merchant

쿠폰 사용과 매출 확인을 실제 상점 스태프 업무로 연결

Operator

OCR·쿠폰·정산 상태를 추적해 행사 운영자가 문제의 위치를 확인

Incident

작은 닉네임 규칙이 가입 전체를 막았다

가입 시 사용자에게 무작위 기본 닉네임을 부여하고 DB에는 중복을 허용하지 않는 제약을 두었습니다. 겉으로 보면 안전해 보였지만 고유값을 만드는 규칙에는 빈틈이 있었습니다. 같은 기본 이름이 다시 뽑혔을 때 이미 접미사가 붙은 기존 닉네임까지 제대로 세지 못해 동일한 후보를 다시 생성할 수 있었습니다.

DB는 이를 중복 오류로 정확히 거부했습니다. 문제는 애플리케이션이 그 충돌을 복구하지 못했다는 점입니다. 가입 예외 처리에는 다른 사용자명 충돌만 사용자 오류로 변환돼 있었고, 닉네임 중복은 재시도 없이 그대로 전파됐습니다. 결과적으로 PASS와 OAuth를 이미 거친 사용자가 마지막 가입 단계에서 실패했고, 실제 가입자 저하의 가장 큰 원인이 됐습니다.

Failure lesson

DB 제약은 잘못된 데이터를 막아줄 뿐이다. 사용자가 정상적으로 다음 상태에 도달하게 만드는 복구 전략까지 있어야 제품의 무결성이 완성된다.

테스트에서 보이지 않았던 경계

코드 조사에서는 두 번째·세 번째 중복 이름 발급, DB unique 충돌, 동시 가입 재시도를 검증하는 테스트가 확인되지 않았습니다. 작은 생성 규칙이 서비스의 가장 중요한 전환인 가입을 막았다는 사실 때문에, 이후에는 핵심 상태 전이에 대해 정상 시나리오뿐 아니라 충돌과 재시도까지 테스트로 고정하는 것을 더 중요하게 보게 됐습니다.

출시 후 퍼널도 개발의 일부

오류 로그만 보고 있었다면 특정 DB 에러가 있다는 사실은 알 수 있지만 그것이 실제 가입률을 얼마나 떨어뜨리는지 늦게 이해할 수 있습니다. 이 경험은 가입 단계별 성공·실패율과 오류 코드를 함께 관측해야 한다는 생각으로 이어졌습니다. 테스트와 운영 관측을 “나중에 추가할 품질 작업”이 아니라 개발 완료 조건으로 보는 근거가 된 프로젝트입니다.

코드 조사에서는 후기 허용 기간의 판정과 실제 등록 조건 사이의 불일치 가능성, 선착순 보상 경계의 동시성 제어처럼 추가로 검증할 한계도 발견됐습니다. 포트폴리오에서는 이를 성과로 포장하지 않고, 실제 운영 시스템을 다시 읽으며 발견한 개선 지점으로 남깁니다.

What this project shows
